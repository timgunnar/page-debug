# 测试失败分类与诊断方法

测试失败涵盖三个层面：元素层、流程层、环境层。按此分类匹配诊断方法。

## 一、元素层：页面变更导致选择器失效

| 子类型 | 典型错误 | 诊断方法 |
|--------|----------|----------|
| XPath/CSS 失效 | `Timeout waiting for locator(...)` | `POST /evaluate` 检查 DOM 中元素是否存在；对比 snapshot 与实际可访问树 |
| 元素文本变更 | 断言 `to_have_text` 失败 | `POST /snapshot` 查看元素当前实际文本；`POST /evaluate` 取 `innerText` |
| 属性变更 | `to_have_attribute` 失败 | `POST /evaluate` 检查元素当前属性值 |
| 元素结构重组 | 选择器存在但不可交互 | 对比 snapshot 中父容器/兄弟元素结构，确认 DOM 树是否调整 |
| 元素被移除 | 选择器完全不存在 | `POST /evaluate` 搜索页面所有相关元素；对比线上版本 |

**诊断策略**：`POST /evaluate` 定位真实元素 → 对比选择器 → 找出差异 → 更新选择器。

### 常见交互模式：批量验证脚本中所有选择器

用户常问"脚本里写的 XPath / 选择器，当前页面都能找到吗"。这是高频问题，Agent 应按以下标准流程处理：

**流程**：
1. `Read` 测试文件，提取所有 `.locator(...)` 调用中的选择器
2. 用一条 bash 命令批量 `/evaluate` 检查每个选择器（`document.querySelector(...) !== null`）
3. 以表格汇总：选择器、行号、存在/不存在
4. 对不存在的选择器，推测正确写法（如 `#22kw` → `#kw`）

**注意**：拼写错误常成对出现（如 `#22kw` 和 `#s222u` 都多了无意义前缀），一个选择器失败后应主动检查脚本中是否还有其他类似错误，而非只看报错行。

### 常见交互模式：执行页面操作流程

用户常问"能不能输入 X 然后搜索""帮我点击 Y 看看结果"。这是高频问题，Agent 应按以下标准流程处理：

**流程**：
1. 确认操作目标和涉及的页面元素
2. `/type` 输入文本 → `/click` 点击按钮，或 `/evaluate` 调用 `form.submit()`
3. `/wait` 等待页面变化，再用 `/status` 或 `/evaluate` 确认结果

**已知限制**：
- 中文文本在 bash curl 中传 JSON 时有编码风险（Windows GBK vs UTF-8），优先用 `/type` 端点（内部已处理事件派发）
- 部分页面（如 Baidu）对合成 `click()` 有校验，`/click` 可能不触发提交，此时改用 `POST /evaluate` 调用 `form.submit()` 或 `POST /press_key Enter`

### 常见交互模式：恢复断点状态

用户手动操作页面后，页面状态已偏离断点位置。每次操作后自动通报当前 URL 和标题，让用户感知页面变化。

恢复有两个级别：

| 端点 | 行为 | 耗时 | 适用场景 |
|------|------|------|---------|
| `POST /reload` | 导航回断点 URL（`location.reload`） | ~2s | 当前页 URL 已变，需快速回原位 |
| `POST /restart` | 杀进程 → 重跑 pytest → 重连 CDP | ~15-20s | 页面状态被彻底改变（SPA pushState、表单已填），需完全重放脚本前置步骤 |

**应注意在每次手动操作后主动告知用户**："已偏离断点页面，可随时让我恢复"。

**流程**：
1. 用户请求操作 → Agent 执行 → 通报结果 + 当前 URL
2. 页面变化后 → 提示"页面已偏离，可随时让我 `/reload` 或 `/restart` 恢复"
3. 用户说"恢复""回去" → 优先用 `/reload`（快）；若页面状态已被彻底改变 → 用 `/restart`（完整）
4. 恢复后通报页面状态

### 常见交互模式：验证业务文件的有效性

用户指认项目中的某个文件（Page Object、业务封装层、组件类等），要求检查其中的选择器和业务逻辑是否在**当前页面**上仍然有效。这与"批量验证测试脚本选择器"不同——目标文件是用户指名的，不是失败测试；且检查深度不只是选择器存在性，还需关联到业务方法。

**流程**：
1. `Grep` + `Read` 定位文件，提取所有选择器定义（`@FindBy`、`page.locator()`、`driver.findElement()` 等）和对应的业务方法名
2. 用批量 `/evaluate` 检查每个选择器在当前页面的 DOM 中是否存在
3. 对不存在的选择器，**关联回业务方法**，输出"`searchPage.searchInput` → `#kw`：存在 / 不存在"的映射
4. 若选择器存在但对应元素不可交互（如 display:none、被遮挡），进一步 `/evaluate` 检查可见性和尺寸
5. 汇总输出：哪些方法受影响、失效原因（选择器过时 / 元素移除 / 交互方式变更）

**关联文档**：对分层架构项目，沿调用链追踪的真实选择器位置见 `references/layered-debugging.md`。

## 二、流程层：业务逻辑变化

| 子类型 | 典型表现 | 诊断方法 |
|--------|----------|----------|
| 步骤增加 | 原 2 步流程变 3 步，中间页/弹窗插入 | `POST /snapshot` 观察当前页面，识别新增中间步骤 |
| 步骤减少 | 合并或跳过某些步骤 | 检查是否可删除多余的脚本步骤 |
| 流程顺序变化 | 原来先 A 后 B，现在先 B 后 A | 对比 snapshot 中页面布局与脚本操作顺序 |
| 前置条件变化 | 原来直接可操作，现在需要登录/授权 | 检查页面是否被重定向、弹窗是否出现 |
| 页面路径变化 | URL 或导航路径变更 | `POST /navigate` 尝试旧路径，观察重定向 |

**诊断策略**：`POST /snapshot` 理解真实流程 → 与脚本对比 → 标记差异 → 调整步骤。

## 三、组件层：封装组件过时

| 子类型 | 典型表现 | 诊断方法 |
|--------|----------|----------|
| 组件选择器过时 | Page Object 选择器在改版后失效 | 穿透封装找到原始选择器，用 `POST /evaluate` 验证 |
| 组件交互方式变更 | 原 click → 现需 hover 后再 click | `POST /snapshot` 观察组件实际交互模式 |
| 组件继承差异 | 父类选择器不适用于当前设备类型 | Grep 检查父子类选择器，分别 `POST /evaluate` 验证 |
| 组件替换 | 整个组件被不同 UI 替换（如表→卡片） | 对比 snapshot 与组件封装代码 |

**诊断策略**：穿透封装层追踪真实选择器 → 逐组件验证 → 更新封装层。

## 四、环境层：运行时环境影响

| 子类型 | 典型表现 | 诊断方法 |
|--------|----------|----------|
| 反爬/验证码 | 页面标题变为"安全验证"或被跳转 | `POST /snapshot` 检查页面标题和关键元素 |
| 页面加载慢 | 间歇性 Timeout | `POST /wait` 等待关键元素；检查网络延迟 |
| 动态 ID/类名 | 每次打开选择器都不同 | `POST /snapshot` 检查选择器是否含随机字符串 |
| 弹窗遮挡 | 元素存在但不可点击 | `POST /snapshot` 检查是否有弹窗/通知层覆盖 |
| iframe 变更 | 元素在 iframe 中但未切换上下文 | `POST /evaluate` 检查元素是否在 iframe 内 |
| 设备/视口差异 | 移动端和桌面端渲染不同 | 检查 viewport 配置 |
| 认证过期 | 被重定向到登录页 | `POST /snapshot` 检查是否有登录表单 |
| 网络/API 变更 | 页面白屏或数据不加载 | `POST /evaluate` 检查网络请求和 API 状态；查看控制台错误 |

**诊断策略**：先排除环境因素（验证码、登录、网络）→ 再定位元素/流程问题。
